# Люди и учётные записи

Решение от 17 ноября 2026 года: человек имеет постоянный внутренний `personId`, необязательный внешний ID с источником и может существовать без учётной записи. У одного человека может быть несколько учёток, например студента и преподавателя. Тип каждой учётки остаётся одним из трёх: студент, преподаватель, настройщик. Автоматического объединения по ФИО нет.

## Данные и совместимость

`personTypes.ts` содержит `Person`, `PersonDraft`, `PersonChange`. Человек хранит имя, ревизию и при наличии `externalReference: { source, value }`. Новые записи из реестра получают UUID. Источник внешнего ID сравнивается после NFKC и приведения к нижнему регистру, само значение ID — точно с сохранением регистра. Пара уникальна среди людей; совпадение выдаёт ошибку, а не объединяет записи. Оба поля внешней ссылки заполняются вместе.

Учётка хранит `personId`, собственные логин, почту, тип, доступ, назначения и учебные реквизиты. Имя в карточке учётки — совместимая проекция имени человека. При изменении общего имени оно атомарно обновляется у всех связанных учёток, их ревизии увеличиваются и появляются события аудита. Почта и логин остальных учёток не меняются. Смена имени снимает старый `scheduleName`, как и прежняя правка имени учётки. Блокировка одной учётки не блокирует остальные.

`AccountsDocument` версии 2 хранит `persons` и `personHistory` вместе с прежними коллекциями. Одна запись localStorage сохраняет человека, учётки и их аудит целиком через общую очередь `executeAdministrationWrite`. Декодер проверяет существование personId, совпадение имени проекции, уникальность внешних ссылок, авторов и последовательность снимков людей. Повреждение не подменяется пустым справочником. Любая запись повторно проходит полный декодер перед сохранением.

Старый формат 1 преобразуется только в памяти: для каждой учётки отдельно создаётся `person:${account.id}` с `legacyAccountId`. Повторное чтение даёт тот же ID. Даже при одинаковом имени учётки не связываются с одним человеком автоматически. Существующие account ID, ревизии, логины, номера зачёток, назначения, результаты, импортные квитанции, учебные события и история не переписываются. История человека за прошлое не выдумывается: у перенесённого снимка ревизия 1 и нет искусственного события создания. Известная дата создания копируется из учётки, отсутствующая остаётся неизвестной. Формат 2 записывается только при следующей подтверждённой операции записи.

Учебные ссылки первого совместимого этапа продолжают использовать прежние account ID. Два студенческих аккаунта человека не объединяют зачётки, оценки или истории обучения. Перепривязка существующих учёток и слияние старых людей отдельным действием сейчас не вводились.

## Интерфейс и сервис

Из реестра учёток открывается `/admin/people`. Здесь есть поиск по имени, внутреннему/внешнему ID, страницы, карточка человека, связанные учётки и последние 20 сохранённых событий с общим числом. Перед добавлением требуется поиск; однофамильцы могут быть отдельными людьми. Создание человека не создаёт логин, приглашение или фиктивное успешное включение входа.

Создание учётки начинается с выбора человека через `PersonLookup`. Показываются имя, внешний ID либо personId и число связанных учёток; поле имени при создании доступно только для чтения. Из карточки человека открывается форма новой учётки с предвыбранным человеком. Сервис повторно проверяет выбранную запись, актуальное имя, глобальную ревизию и действующего настройщика. При редактировании имени существующей учётки форма предупреждает об изменении во всех учётках этого человека.

`accountService.listPeople` выполняет поиск/пагинацию на стороне адаптера и возвращает только страницу людей, их связанные учётки, ревизии и ограниченную историю выбранного человека. `savePerson` авторизует изменение внутри общей очереди. `usePeopleQuery` подписывается на изменения учёток, отбрасывает поздние ответы и не принимает устаревшую ревизию как новую базу открытого редактора. Ошибка и внешняя правка сохраняют ввод; для изменившейся целевой карточки требуется открыть актуальный источник заново. Навигация с изменениями использует общий guard.

Обычное ручное создание учётки требует явного выбора personId. Существующий пакетный импорт создаёт отдельного человека для каждой новой учётки с новым внутренним ID; по ФИО существующие люди не сопоставляются. Это явно указано на странице импорта. Квитанции и повтор пакета сохраняют прежнюю идемпотентность. Сопоставление импорта по подтверждённым внешним ID остаётся в U07. Демо-команды используют ту же доменную связь; для старого демо со стабильными account ID применяется стабильный namespaced personId.

## Резервные копии и сервер

Инспекция архивов принимает форматы учёток 1 и 2 и проверяет всю схему до сравнения отдельных записей. Сравнение дополнено `persons`, `person-history` и полем `personId` у учётки. В техническом отчёте находятся ID, счётчики и названия изменённых полей; имена, внешний ID и снимки доступны только при явном просмотре конфликта через существующий сервис. Сравнение старого источника использует помеченный снимок миграции, без вымышленной ранней истории. Это не подтверждает полномочия и не разрешает восстановление. Проверка согласованности выбранных версий людей, связей учёток и их аудита перед применением архива остаётся в G03.

U08 должен перенести эту атомарную операцию на сервер: проверка автора и прав, доверенное время, уникальная пара внешнего источника/ID, стабильные person/account ID, ревизии/ETag, идемпотентность создания и серверные поиск/страницы. `personId` не заменяет учётку в авторизации. Реальные приглашения, пароли и активация входа относятся к серверному этапу.

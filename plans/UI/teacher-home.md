# UI/UX-аудит: «Главная» преподавателя (`/`)

**Область:** только `frontend/src/pages/home/index.tsx`, `index.module.scss` и используемые на этой странице `SearchWidget`, `TodaySchedule`/`ScheduleWidget`, `CalendarWidget`, `PlannerAgenda`, форма создания задачи и сообщения об ошибках. Анализ исходников и стилей, без браузерной проверки и запуска тестов. Другие вкладки не анализировались; ссылки на них ниже описывают только назначение перехода с главной. Приоритет: **P0** — вводит в заблуждение или блокирует сценарий, **P1** — существенно затрудняет ориентирование/доступность, **P2** — визуальная полировка.

## P0 — исправить смысл и основные сценарии

1. **Показатели «сегодня» расходятся с выбранным календарным днём.** `frontend/src/pages/home/index.tsx`: `activeDate = selectedDate ?? now`, в `TodaySchedule date={activeDate}` и `PlannerAgenda date={activeDate}` передаётся выбранный день, но `.flexParams` выводит `dashboard.todayLessons`, `conductedLessons`, `attendanceMarked`, `gradesCount` из `getTeacherDashboard(... now ...)`. После выбора вчера/завтра календарь, расписание и задачи меняются, а три соседних показателя остаются сегодняшними без пояснения. Выбрать явный контракт: либо неизменный блок «Показатели на сегодня» с видимым заголовком, датой и отделением от обзора выбранного дня, либо вычислять доступные показатели для выбранной даты; не переименовывать накопительные журнальные метрики в дневные. В заголовке обзора показывать выбранную дату и кнопку «Вернуться к сегодня». Критерий: после выбора другой даты пользователь однозначно понимает период каждой цифры.
2. **Пустое расписание превращается в пустую карточку.** `frontend/src/components/TodaySchedule/index.tsx`: в `.body` при `!scheduleError && !schedule.length && !nextDate` не выводится ничего; `nextDate` ищется только в следующие 14 дней. `frontend/src/components/TodaySchedule/index.module.scss`: `.container { height: 300px; }` оставляет большую пустую область. Отдельно показывать «На [дата] занятий нет» независимо от того, найден ли следующий день; при наличии следующего дня добавлять ссылку, при отсутствии — ссылку на полное расписание. Различать «нет занятий» и «нет данных» (уже есть ошибка). Критерий: для любого пустого дня остаётся содержательное состояние и следующий шаг.
3. **Ошибки и неполные данные не должны выглядеть как обычный обзор.** `frontend/src/pages/home/index.tsx`: `.focusHeader > strong` становится «—» при `focusError`, но `.focusList` всё равно показывает оставшиеся пункты; `.flexParams .summaryValue` заменяет недоступные показатели на «—» без объяснения непосредственно рядом с цифрами. `DashboardReadError` находится только внутри фокус-карточки; ошибки расписания и планировщика показываются внутри соответствующих виджетов. Дать каждому затронутому показателю текст «Данные недоступны»/подсказку и локальное действие повтора либо привязать метрику к общему сообщению через `aria-describedby`; для фокуса пояснить «Показаны доступные данные» вместо неинтерпретируемого «—». Не скрывать корректные частичные данные. Критерий: по каждому прочерку понятны причина и восстановление.

## P1 — иерархия, доступность, отзывчивость

4. **Главной не хватает собственного контекстного заголовка.** `frontend/src/pages/home/index.tsx`: внутри `.pageContainer` сразу начинается `.dashboardGrid`, первая карточка — переключатель поиска, далее заголовки `h2` расписания, планировщика, фокуса и календаря; локального `h1` и общего указания выбранного дня нет. Добавить верхний `DashboardHeader` с `h1 «Главная»`, читаемой датой/периодом обзора и возвратом к сегодняшнему дню. Разделить основные секции (`aria-labelledby` на заголовки), сохранив семантику карточек; существующую навигационную шапку приложения не дублировать. Критерий: и зрительно, и в списке заголовков ясно, что обзор относится к выбранному дню.
5. **Порядок карточек на узком экране отодвигает действия.** `frontend/src/pages/home/index.tsx`: `.leftColumn` содержит поиск → расписание → задачи → показатели, `.rightColumn` — «Что требует внимания» → календарь. `index.module.scss`: при `max-width: 980px` сетка становится одноколоночной без перестановки; календарь, который управляет датой уже показанных карточек, оказывается последним, а «Что требует внимания» — после статистики. Спроектировать мобильный поток: заголовок/выбор дня → фокус → расписание → задачи → краткие показатели → поиск (или поиск выше при подтверждённом частом сценарии). Реализовать область сетки/упорядоченную DOM-структуру без расхождения клавиатурного и визуального порядка; проверить при 320–620 px и 200% масштабе. Критерий: выбор дня происходит до зависимых карточек, срочное действие видно без прокрутки всего дашборда.
6. **Поиск не объясняет пустой запрос и не отражает действие.** `SearchWidget/index.tsx`: `.toggleRow` переключает «Поиск по аудитории»/«Поиск по группе», `search.tsx` подписывает поле только «Группа»/«Аудитория», кнопка имеет `aria-label="Найти расписание"`; `home/index.tsx` по `onSearch` с пустой строкой открывает расписание на `activeDate` без фильтра. Добавить заголовок секции «Поиск расписания», краткую подсказку «Введите группу или аудиторию», кнопку с текстом «Найти» на широком экране (иконка + доступное имя на узком); пустой запрос либо валидировать с пояснением, либо явно назвать действием «Открыть расписание». Сохранить переключение через `aria-pressed` и явную метку поля. Критерий: результат Enter/клика предсказуем с пустым и непустым запросом.
7. **Постоянная высота расписания создаёт вложенную прокрутку и нерациональную пустоту.** `TodaySchedule/index.module.scss`: `.container { height: 300px; }`, `.body { min-height: 0; }`; `ScheduleWidget/index.module.scss`: `.scheduleWrapper { overflow-y: auto; }`, `.fill { height: 100%; }`. При нескольких занятиях приходится прокручивать список внутри прокрутки страницы; при одном — остаётся большой резерв. На компактном/мобильном экране предпочесть высоту по содержимому и ограниченное число строк с «Все занятия»; на широком экране ограничивать высоту только осознанно и явно обозначать прокручиваемую область. Критерий: ближайшее занятие доступно без прокрутки внутри карточки, пустое состояние не занимает 300 px.
8. **Интерактивные элементы календаря и задач слишком мелкие визуально и местами физически.** `CalendarWidget/index.module.scss`: `.navButton` 32×32 px, `.calendarDay` минимум 42 px, `.legend button` с `font-size: .62rem` и padding 4×8; `.daySummary p` — `.62rem`. `PlannerAgenda/index.module.scss`: `.actions button` с `.65rem` и padding 7×10, `.empty .planButton` padding 3×7, `.task small` `.61rem`; `home/index.module.scss`: `.summaryLabel` `.65rem`, `.focusList span` `.66rem`, `.taskNotice` `.65rem`. Увеличить минимум интерактивной области до 44×44 CSS px для навигации календаря, «Сегодня» и компактных действий; вторичный текст до читаемой шкалы (~12–14 px при обычном масштабе, минимум по токенам), обеспечить перенос строк. Критерий: управление пальцем и чтение при 200% масштабе без наложений; контраст проверить в обеих темах.
9. **Планировщик маскирует изменение временного контекста.** `PlannerAgenda/index.tsx`: когда `dayNotes.length === 0`, `upcoming = true` и `.tasks` показывают до трёх будущих задач через `getNextPlannerNotes(notes, date)`; при отсутствии таких задач заголовок остаётся «Ближайшие задачи», но `.empty` говорит «Задач на этот день нет». Для выбранной даты заголовок/пустое состояние должны однозначно отделять «На выбранный день задач нет» от отдельного блока «Далее» с датами задач; если будущих задач нет — писать «Предстоящих задач нет». Явно показывать выбранную дату в блоке. Критерий: не возникает впечатления, что будущие задачи назначены на выбранный день.
10. **Резюме календаря повторяет числа, но не помогает перейти к действиям.** `CalendarWidget/index.tsx`: `.daySummary` после выбора дня показывает «Занятия: …, задачи: …» и фразу «Выберите день, чтобы увидеть…», хотя день уже выбран; `home/index.tsx` обновляет URL `date` и зависимые карточки. Для выбранного дня заменить инструкцию на обратную связь «Обзор выше обновлён»/«Перейти к занятиям/задачам» с якорями к секциям и управлением фокусом по сценарию выбора. Не перемещать фокус принудительно при обычной клавиатурной навигации по датам; учесть `aria-live` и не дублировать подробные объявления каждой кнопки. Критерий: после выбора понятно, где увидеть результат, особенно на мобильном экране.
11. **Важность фокуса обозначена почти только цветной точкой.** `home/index.tsx`: `.focusList i` получает `urgent`/`warning`, но этот элемент не содержит текста; `index.module.scss`: `.urgent` и `.warning` различаются лишь фоном. Добавить видимый текстовый статус «Срочно»/«Нужно заполнить» там, где смысл действительно зависит от приоритета; оставить точку лишь как дополнение (`aria-hidden`). Счётчик `.focusHeader > strong` подписать для скринридера как число доступных задач внимания, не просто голое число. Критерий: срочность понятна без цвета и из доступного имени элемента.
12. **Уведомление о сохранении задачи не привязано к жизненному циклу формы.** `home/index.tsx`: `saveTask` закрывает `PlannerNoteForm` и показывает `.taskNotice[role="status"]`; уведомление остаётся до ручного закрытия, даже после переключения даты. Текст «Добавлено на …» и ссылка на задачу полезны — сохранить, но ограничить показ текущим событием, сделать кнопку закрытия с видимым фокусом и доступной областью, не позволять уведомлению неожиданно отодвигать карточки. `home/index.module.scss`: `.taskNotice button` — 24×24 px без локального `:focus-visible`. Критерий: сохранение озвучено, ссылка доступна, уведомление не превращается в устаревший элемент обзора.

## P2 — визуальная система именно этого обзора

13. **У метрик не хватает структуры и единиц измерения.** `home/index.tsx`: `.flexParams` выводит значения `x / y`, «Нет пар», «—», но не раскрывает числитель/знаменатель; третья подпись «Оценки · практики и лабораторные» не поясняет, что означает доля. Представить три метрики как компактные `StatCard`/`dl` с точным заголовком периода, явными «проведено из запланированных», «отмечено из доступных», «выставлено из возможных» (после проверки доменного смысла полей); не полагаться только на визуальный слеш. `home/index.module.scss`: `.paramBox` и `.summaryLabel` перенести на общую шкалу размеров текста. Критерий: значение можно прочитать без знания реализации.
14. **Календарная легенда теряется на фоне сетки.** `CalendarWidget/index.module.scss`: `.dots i, .legend i` всего 4×4 px, `.legend` `.62rem`; `CalendarWidget/index.tsx` содержит словесные значения, а день имеет доступное имя с числами. Увеличить визуальные маркеры и читаемость подписей; различать занятия/задачи также формой или мини-числом в дневном обзоре, сохранив числовые `aria-label`/`daySummary`. Критерий: тип события различим без угадывания цвета.

## Предлагаемая компонентная архитектура

- **`TeacherHomePage` — композиция и данные:** `activeDate` синхронизирован с `?date`, обновление источников и сохранение задачи остаются в контейнере (`home/index.tsx`); единая модель `DashboardDayView` содержит дату, состояния источников, занятия, задачи и сводку. Текущие *today*-показатели держать отдельно от выбранного дня, чтобы не смешивать периоды. Не переносить загрузку и маршрутизацию в карточки.
- **`DashboardHeader` + `DayContextBar`:** заголовок страницы, дата выбранного дня, возврат к сегодня, доступное объявление смены даты. Один источник истины для `TodaySchedule`, `PlannerAgenda`, `CalendarWidget`; для выбора даты сохранять URL и ожидаемое поведение Back/Forward (сейчас `setParams(..., { replace: true })` заменяет историю — решить явно, требуется ли история выбора дней).
- **`DashboardLayout` + `DashboardSection`:** адаптивное упорядочивание карточек по сценарию, общий заголовок/действие/состояние (loading/empty/error/partial) и якорь секции. Содержимое специализировано: `SchedulePreview`, `AgendaPreview`, `FocusList`, `CalendarDayPicker`, `DailyStats`, `ScheduleSearch`. `CalendarDayPicker` остаётся единственным полноценным календарём, а не копируется в каждой карточке.
- **Общие контракты интерактивности:** `SearchWidget` использует `SearchField` и `SegmentedControl`; календарь и планировщик используют общие `Button`/`IconButton` для размеров и focus-visible; `StatCard` и `StatusBadge` задают визуальную семантику. `PlannerNoteForm` сохраняет собственную валидацию и модальность, на главной остаётся лишь команда «Создать задачу» и подтверждение сохранения. Локальный SCSS задаёт сетку и особенности виджетов, не глобальные размеры контролов.
